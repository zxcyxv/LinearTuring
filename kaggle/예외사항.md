## 3. `notebook_launcher` 의 CUDA 사전 초기화 제약 ★

`accelerate.notebook_launcher` 는 다중 GPU 일 때 **fork** 로 자식 프로세스를 띄운다. fork 시점에 부모
(노트북 커널)에서 CUDA 컨텍스트가 이미 만들어져 있으면 자식에서
`Cannot re-initialize CUDA in forked subprocess` 로 죽는다. accelerate 공식 문서가 명시한 제약이다.

**규칙**

1. `train_kaggle.py` 를 붙여넣은 셀보다 **앞선 어떤 셀에서도** `torch.cuda.*` 를 호출하지 말 것.
   `torch.randn(...).cuda()`, `torch.zeros(..., device="cuda")`, `torch.cuda.empty_cache()`,
   `model.to("cuda")` 전부 해당한다. `!nvidia-smi` 는 별개 프로세스라 무해하다.
2. 이미 만졌다면 **커널을 재시작**해야 한다 (Run → Restart & Clear Cell Outputs). 정리 함수로는 안 풀린다.

**[2026-09-04 캐글 실측] 우리 코드 자신이 이 제약을 어기고 있었다.**
`run()` 의 `torch.cuda.device_count()` 가 **torch 2.10(캐글)에서 CUDA 를 초기화한다.** 로컬 2.8 에서는 안 그래서
"NVML 경로라 무해하다"고 적어 뒀는데 틀렸다. 그 결과 fork 자식 4개가 전부 이렇게 죽었다:

```
[LT] num_processes=4
Launching training on 4 CUDAs.
RuntimeError: Cannot re-initialize CUDA in forked subprocess.
```
(뒤이어 뜨는 `accelerate 사용 불가 → torch.distributed 폴백` 은 부수 증상이다 — 자식이 이미 bad fork 라
`Accelerator()` 도 폴백의 `torch.cuda.set_device` 도 같은 이유로 실패한다.)

**조치 (반영됨)**
- GPU 수는 `_gpu_count()` 가 `CUDA_VISIBLE_DEVICES` 또는 `nvidia-smi -L`(별개 프로세스)로 센다. 부모는 `torch.cuda` 를 일절 안 건드린다.
- `run()` 진입 시 `torch.cuda.is_initialized()` 로 먼저 검사해, 걸리면 **fork 하기 전에** "커널을 재시작하라"는 한 줄로 죽는다.
- 급하면 `CFG["num_processes"]=4` 로 명시해도 된다 (`device_count()` 호출을 건너뛴다).

**버전 주의**: 로컬 검증은 torch 2.8, 캐글은 **2.10.0+cu128** 이다. 이 종류의 차이가 또 나올 수 있다.
3. `train_kaggle.py` 자체는 import 시점에 CUDA 를 건드리지 않도록 짜여 있다. GPU 를 쓰는 코드는 전부
   `main()` 안이다. 유일한 예외가 `run()` 의 `torch.cuda.device_count()` 인데, 이것은 NVML 경로라
   컨텍스트를 만들지 않는다 (accelerate 자신도 스폰 직전에 같은 호출을 한다).
4. 진단이 필요하면 셀 맨 위에 `import os; os.environ["ACCELERATE_DEBUG_MODE"]="yes"` 를 두면
   진짜 학습 전에 더미 스폰으로 사전 점검한다.

**같이 알아 둘 사고 하나**: accelerate 가 분산 환경을 못 알아채고 `num_processes=1` 로 떨어지는 사례가
보고되어 있다(Kaggle 에서 `num_processes=2` 인데 "Launching training on one GPU"). 그대로 두면 랭크마다
자기가 유일한 프로세스인 줄 알고 1/N 데이터로 학습하고 **모든 랭크가 체크포인트를 덮어쓴다.**
`train_kaggle.py` 의 `init_distributed` 는 accelerate 가 보고한 world_size 를 런처가 심은 환경변수
`WORLD_SIZE` 와 대조해서, 어긋나면 경고를 찍고 `torch.distributed` 로 직접 프로세스 그룹을 세운다.
로그에 `[LT] 경고: accelerate 가 world_size=... 로 보고했으나 ...` 가 뜨면 그 경로로 빠진 것이다(정상 동작).
`[LT] world_size=N local_bs=M` 줄이 **기대한 N** 인지 매 세션 확인할 것.

## 4. 12시간 제한과 재개

### Kaggle 쪽 사실

- 세션 최대 실행시간은 공식 Product Update 기준 **약 12시간**(과거 9시간에서 상향). 출처 간 표기가
  엇갈리므로 **노트북 UI 의 세션 타이머로 직접 확인**할 것.
- **인터랙티브(편집) 세션은 약 1시간 idle 타임아웃**이 있다. 장시간 학습은 반드시
  **Save Version → "Save & Run All (Commit)"** 로 백그라운드 배치 실행해야 한다.
  인터랙티브 세션에서 만든 `/kaggle/working` 파일은 커밋하지 않으면 **세션 종료와 함께 사라진다.**
- 커밋 실행이 끝나면 `/kaggle/working` 의 내용이 그 버전의 **output** 으로 영구 보존된다 (상한 약 20GB,
  최상위 파일 개수 제한 있음 — 우리는 체크포인트 2개뿐이라 여유).

### 이 코드의 대응

- 체크포인트는 `/kaggle/working/checkpoints/step_<N>.pt` (기본값; `CFG["out_dir"]` 로 변경).
  **파일 1개 ≈ 143 MB** (raw + EMA + EMA shadow + AdamATan2 모멘트 2개). `keep_last=2` → 최대 ~286 MB.
- 저장 시점: (a) eval 구간 경계(= `eval_interval` 에폭마다 = 1,953 step), (b) `save_every_steps`(기본 2000),
  (c) `max_hours` 도달, (d) 종료 직전. 임시파일에 쓰고 `os.replace` 하므로 중간에 잘려도 반쪽 파일이 안 남는다.
- `CFG["max_hours"]` (기본 **11.0**) 이 지나면 저장하고 **정상 종료**한다. 12시간 벽에 맞아 죽으면 마지막
  저장 이후가 날아가므로 여유를 둔 것이다. 정지 판정은 랭크 0 이 내려 브로드캐스트한다(랭크 간 불일치 → 교착 방지).

### 다음 세션에서 잇는 법

1. 이전 세션을 **Save Version (Save & Run All)** 으로 끝낸다.
2. 새 노트북(또는 같은 노트북의 새 버전) 편집기에서 **Add Data → Notebooks 탭 → 이전 노트북 선택**.
   `/kaggle/input/<이전-노트북-슬러그>/checkpoints/step_*.pt` 로 마운트된다.
   (더 안정적으로 하려면 이전 버전의 Output 페이지에서 **"New Dataset"** 으로 승격시켜 Dataset 으로 붙인다.)
3. 셀에서 한 줄 지정:
   ```python
   CFG["resume_from"] = "/kaggle/input/<이전-노트북-슬러그>/checkpoints"
   ```
   `find_latest_checkpoint` 가 `out_dir` 과 `resume_from` 을 **둘 다** 뒤져 step 번호가 가장 큰 것을 고른다.
   같은 세션 안에서의 재시작은 `resume_from` 없이도 `/kaggle/working/checkpoints` 에서 자동으로 잇는다.
4. 재개하면 로그에 이렇게 뜬다:
   ```
   [LT] 체크포인트 재개: /kaggle/input/.../step_123456.pt
   [LT] EMA shadow 복원
   [LT] 시작 step=123456 iter=63 batch_in_iter=207
   ```
   `step` 이 0 이 아니면 정상. 데이터 스트림은 `iter`·`batch_in_iter` 로 되감으므로 **같은 에폭을 두 번 돌지 않는다**
   (되감기는 난수만 소비하고 보드는 안 만든다 — 수 초).
5. **재개 검증 (필수, `HANDOVER.md §2` 의 무학습 판정법)**: 재개 후 첫 체크포인트의 `raw_model_state_dict` 가
   로드한 값과 **달라야** 정상이다.
   ```python
   import torch
   a = torch.load("<로드한 체크포인트>", map_location="cpu", weights_only=False)["raw_model_state_dict"]
   b = torch.load("<재개 후 첫 체크포인트>", map_location="cpu", weights_only=False)["raw_model_state_dict"]
   diff = [k for k in a if not torch.equal(a[k], b[k])]
   print("무학습" if not diff else f"정상 ({len(diff)}/{len(a)} 텐서 변화)")
   ```
   정상이면 18개 중 **16개**가 변한다. 안 변하는 2개는 정상이다:
   `model.inner.beta` (`stdp_window="psi"` 면 forward 에 안 나와 grad 가 없다 — 설계대로),
   `model.inner.init_hidden` (파라미터가 아니라 버퍼).

| 11 | **다중 프로세스 경로 (CPU + gloo 대체 검증)** | world_size 1 / 2 / 4 에서 1 step 후 파라미터 **bit-exact 동일** → loss_scale `1/global_batch_size` + `all_reduce(SUM)` 의미론이 URM 과 같음을 확인. 소형 모델 `main()` 전체를 4 프로세스로 140 step 돌린 결과가 1 프로세스와 **최대 절대차 2.4e-07**(부동소수 합 순서 차이뿐), 로그의 `lm_loss`·`[EVAL]` 값도 동일 |

| 13 | 스파스 임베딩 sign-SGD 경로 | `puzzle_emb.weights` 832개 전부 갱신됨(norm 0.1136 → 0.1235). 다중 랭크 `all_gather_into_tensor` 경유 결과도 1랭크와 동일 |

### 못 한 것 / 미검증 ✘

| 항목 | 왜 |
|---|---|
| **실제 4-GPU(NCCL) 실행** | 이 머신에 L4 **1장**뿐. 다중 프로세스 경로는 CPU+gloo 로 대체 검증했다(위 #11·#12). NCCL 고유의 문제(P2P/IB 비활성, 포트 충돌, GPU 당 프로세스 배치)는 **미검증**. Kaggle 첫 실행 때 `[LT] world_size=4 local_bs=32` 가 찍히는지 반드시 확인할 것. |
| **`notebook_launcher(num_processes=4)`** | GPU 가 없어 못 돌렸다. `num_processes=1` 경로만 확인. fork 제약(§3)이 여기서 걸릴 수 있는 유일한 지점이다. |
| **실제 Kaggle 노트북에서의 실행 전체** | Kaggle 계정/세션이 없다. 경로(`/kaggle/input`, `/kaggle/working`)·패키지 버전·L4×4 옵션 존재 여부 전부 현장 확인 필요. |
| **긴 학습에서의 수렴 재현** | 170 step 까지만 돌렸다. 저장소 기록(76k step 셀 0.800 / exact 835-959)과의 곡선 일치는 **미검증**. 초기 손실·지표가 원본과 bit-exact 이므로 궤적이 어긋난다면 원인은 데이터 순서(증강 풀)뿐이다 — §7 참조. |
| **4-GPU 스텝 시간 실측** | 측정 도중 같은 GPU 에 다른 학습(URM `pretrain.py`)이 붙어 오염됐다(382 ms/step 으로 2.2배 느려짐 — `HANDOVER §3` 의 "같은 GPU 에 분석 스크립트" 항목과 같은 현상). §6 의 4-GPU 추정은 **실측이 아니라 추정**이다. |

## 6. 예상 학습 시간

### 근거

- 총 스텝: `int(epochs × 1000 / 128) = 390,625`. 실제로는 eval 구간마다 마지막 부분배치를 버려
  **200 iter × 1,953 = 390,600 step** 을 돈다 (`HANDOVER` 의 "계획 390,600 step" 과 일치).
- **1×L4 실측(오염 없는 구간)**: 배치 128, `torch.compile`, `stdp_window=psi` → **175 ms/step (5.7 it/s)**, peak 3.82 GB.
- eval 비용: 2,048 예제 ÷ 128 = 16 배치 × 16 세그먼트 = 256 forward. 실측으로 eval 1회 ≈ **35~40초**.
  200회 전부 하면 ~2시간. `eval_interval` 을 키우면 줄어든다.

### 1×L4

- `max_hours=11` → 11h × 3600 ÷ 0.175 ≈ **226,000 step** (eval 시간 빼면 ~215,000). 390,600 의 약 **55%**.
- 완주에 **약 2 세션(≈19~20 GPU-시간)**. 주당 30시간 쿼터 안에서 한 주에 끝난다.

### 4×L4 (추정 — 실측 아님)

데이터 병렬이므로 프로세스당 배치는 128/4 = **32**. 스텝당 시간은
`t₄ ≈ (배치 32 의 GPU 계산 시간) + (그래디언트 all-reduce)` 이다.

- 계산 항: 이 모델은 배치 방향으로 거의 선형이다(주 비용이 `addr` 사영과 T×T einsum 으로 전부 배치에
  비례하는 GEMM). 다만 배치 32 에서는 GPU 점유율이 떨어져 완전한 1/4 은 안 나온다. **1/4 ~ 1/2.5**
  범위로 잡으면 44 ms ~ 70 ms.
- 통신 항: 파라미터 7,155,245개 × 4 B = **28.6 MB**. ring all-reduce 는 스텝당 `2(N−1)/N × 28.6 MB ≈ 43 MB`
  를 옮긴다. L4 는 NVLink 가 없어 PCIe(gen4 x16, 실효 ~20 GB/s)로 간다 → **~2 ms** + 텐서 18개 각각의
  집합 호출 지연 ≈ 수 ms. 합쳐 **5~10 ms**.
- → **t₄ ≈ 50~80 ms/step**, 즉 **12~20 it/s**. 1장 대비 **2.2~3.5배**.
- `max_hours=11` 이면 **495,000 ~ 790,000 step** 상당 → **390,600 완주가 한 세션(11시간) 안에 들어간다**
  (여유가 넉넉하지 않으므로 §4 의 재개는 그대로 살려 둘 것).

**이 추정의 신뢰도**: 계산 항의 스케일링 계수(1/4~1/2.5)가 가장 큰 불확실성이다. Kaggle 에서 첫 200 step 의
tqdm it/s 를 보고 바로 재추정하라. 통신 항은 파라미터 수와 PCIe 대역이 확정값이라 오차가 작다.

### 줄이는 손잡이

- `CFG["eval_interval"]` 을 250 → 500 으로 하면 eval 횟수가 절반(총 200회 → 100회)이 되고
  체크포인트 저장 횟수도 준다. **다만 `epochs` 의 약수여야 한다** (assert 로 막아 뒀다).
- `CFG["compile"]=False` 는 하지 말 것 — 첫 컴파일에 ~45초 들지만 스텝이 훨씬 느려진다.

## 7. 그 밖에 사람이 챙겨야 할 것

1. **`core/minimal.py` 와의 동기화.** 이식본은 `core/minimal.py` (sha256 `036988ac048ec94e…`, 2026-09-04,
   `block_order` 플래그 추가분 포함) 를 그대로 옮긴 것이다. 저장소의 모델이 바뀌면 이식본도 다시 떠야 한다.
   바꾼 것은 딱 세 군데이고 전부 수치와 무관하다:
   (a) `LTConfig` 의 베이스 `pydantic.BaseModel` → `dataclass`,
   (b) `LT.__init__` 의 `LTConfig(**d)` → `LTConfig.from_dict(d)`(모르는 키 무시),
   (c) URM import 2개(`trunc_normal_init_`, `CastedSparseEmbedding`)를 파일 안의 동등 구현 참조로.
   재동기화는 `core/minimal.py` 에서 `@dataclass class LTCarry:` 이후 전체를 떠서 위 세 치환을 다시 걸면 된다.
   **바꾼 뒤에는 반드시 수치 대조(§5 #1·#2)를 다시 돌릴 것.**

2. **체크포인트 키 접두가 저장소와 다르다.** 저장소 체크포인트는 `_orig_mod.model.inner.*` 인데
   이 코드는 컴파일 이전 모듈로 저장하므로 `model.inner.*` 다. `strip_prefix()` 가 `_orig_mod.` 를 떼므로
   **저장소 체크포인트를 이 코드로 읽는 것은 된다**(웜스타트 가능). 반대로 이 코드의 체크포인트를
   `analysis/*.py` 로 읽으려면 `sudoku/lt.py: load_lt` 계열의 접두 정리가 이미 그 일을 한다.
   `model_state_dict` 에는 저장소 규약대로 **EMA 가중치**를 넣었다.

3. **증강 풀의 성격.** 원본은 빌드 시점에 퍼즐당 증강 1,000개를 뽑아 **고정**한다(같은 aug_idx → 항상 같은 판,
   50,000 에폭 동안 각 증강 ~50회 반복). 이 코드는 `(퍼즐 id, aug_idx)` 로 결정되는 Philox 스트림에서 변환을
   뽑아 그 **고정 풀을 재현**한다. 매번 새로 뽑는 무한 풀로 하면 과적합 압력이 달라져 저장소 곡선과의 비교가
   깨지므로 일부러 이렇게 했다. 단, **어떤 1,000개 판이 풀에 들어가는지는 원본과 다르다**
   (원본은 `np.random` 전역 스트림, 여기는 Philox). 변환의 분포는 같은 균등분포이고, 뽑히는 원본 퍼즐 1,000개와
   그룹 순서·aug_idx 추출 순서는 URM 과 동일하다. → 곡선이 통계적으로 같아야 하지만 **step 단위로 bit-exact 하지는 않다.**

4. **테스트셋 유출.** 증강은 train 에만 건다(원본 `num_augments = num_aug if set_name=="train" else 0`).
   `2026-09-01/README §7` 의 점검(테스트 ∩ 학습 = 0, 궤도 동치 전수 검증 0)이 그대로 유효하다:
   그 점검은 "테스트 퍼즐이 학습 퍼즐의 **궤도**(자릿수 9! × 전치 2 × 밴드 1296 × 스택 1296) 안에 있는가" 를
   물었고, 궤도는 대표원을 어떻게 뽑든 같은 집합이므로 우리가 새로 뽑는 어떤 증강도 이미 "테스트와 서로소" 로
   검증된 궤도 안에 머문다.

5. **학습 로그의 `acc` 는 16 스텝에 한 번만 유효하다.** ACT 가 없어 `halted` 는 `loops=16` 스텝마다 한 번만
   참이고, URM 의 지표는 halted 레인만 센다. URM 은 `step % 200 == 0` 에 찍어서 (200 이 16 의 배수가 아니라)
   train acc 가 **항상 0** 으로 나왔다(`HANDOVER §3` 의 "재개 로그의 train acc 0.0000"). 이 코드는 마지막
   halted 스텝의 지표를 보관해 `[halt step N]` 을 붙여 찍는다. **지표 정의 자체는 안 바꿨다.**

6. **`[EVAL]` 출력 시점.** 저장소 패치는 `dist.reduce` **전에** 찍어서 다중 GPU 에서 랭크 0 의 지역 수치만
   보여준다(4랭크면 `exact x/512`). 이 코드는 reduce 후에 찍는다 → 항상 `exact Y/2048`. 1 GPU 에서는 동일.

7. **`torch.compile` 첫 컴파일 ~45초.** tqdm 이 처음 몇 스텝 동안 멈춘 것처럼 보이는 게 정상이다.
   train / eval 두 모드에 각각 그래프를 뜨므로 첫 eval 에서도 한 번 더 멈춘다.

8. **`DataLoader` 워커 1개 고정.** `CFG["dataloader_workers"]` 를 1 초과로 올리지 말 것 — 데이터셋이
   단일 워커를 가정하고 난수 스트림을 만든다(URM 도 같은 assert 를 둔다). 0 으로 두면 증강 생성이
   메인 프로세스에서 돌아 스텝당 ~10 ms 가 더 붙는다.

9. **TF32 를 켜지 않았다.** URM `pretrain.py` 가 안 켜므로 그대로 뒀다(bf16 autocast 안에서 도는 GEMM 이
   대부분이라 영향은 작다). 저장소 벤치(`2026-09-04/analysis/bench_train.py`)는 TF32 를 켜므로 그쪽과
   미세한 수치 차이가 날 수 있다 — **학습 수치는 URM 쪽에 맞췄다.**

## 코드 동기화 (2026-09-04 후반) — 기본 설정이 `DEEP2_d832` 로 바뀜

`core/minimal.py` 가 이 파일 작성 이후 크게 바뀌어 모델 섹션을 통째로 다시 옮겼다.
**`LTLayer` + `LT_Inner` 는 `core/minimal.py` 에서 그대로 복사한 것**이고, 4개 설정에서 로짓이 **비트 동일**함을 확인했다

### 바뀐 것

| | 이전 | 지금 | 이유 |
|---|---|---|---|
| Φ 계수 `γ` | 학습 (init 0.1) | **`1/d` 고정** | 스케일 게이지. 학습시키면 1,000배 미끄러진다. 반경이 `√d` 가 되어 RMSNorm 과 같은 자리 |

| **`num_layers`** | 없음 | **2** | 물리 레이어 2벌. 총 블록 적용 = `blocks_per_seg × num_layers` = 16 |
| 폐기 키 | — | `gamma_init`·`inj_gate_init` 제거 | 남아 있으면 조용히 무시되므로 CFG 에서 지웠다 |

|---|---:|---:|---:|
| `num_layers=1` (이전 기본) | 7.16M | 5.65 it/s | 19.2 h |
| **`num_layers=2` (지금 기본)** | **14.29M** | **2.82 it/s** | **38.5 h** |

블록 적용이 8 → 16 이라 스텝당 연산이 정확히 2배다. 4×L4 로 나눠도 **한 세션(12h)에 완주가 안 된다** —
`max_hours` 로 저장하고 끊은 뒤 `resume_from` 으로 이어야 하며, **최소 2~3 세션**을 예상해야 한다.
예산이 한 세션이어야 하면 `CFG["num_layers"]=1` 로 되돌리거나 `epochs` 를 줄여라.

메모리는 배치 128 단일 GPU 기준 8.74 GB(= `num_layers=1` 의 4.80 GB 대비 1.8배). 프로세스당 배치 32 면 여유 있다.
